# ADR-0003. Единый HTTPS-клиент с закреплённым IP для DoH и проверки сервисов

## Контекст и постановка задачи

Как проверить, что сервис открывается именно через проверяемый DNS, и не писать два сетевых клиента для DoH и для HTTPS? (REQ-FUNC-001, REQ-INT-004)

## Драйверы решения

* проверка должна идти на IP, полученный от проверяемого DNS, а не от системного
* TLS средствами Windows (Schannel), без OpenSSL
* отмена не дольше 1,5 с (REQ-PERF-002)

## Рассмотренные варианты

* Один клиент pinnedHttp(ip, url) на QSslSocket (Schannel) для DoH и /cdn-cgi/trace
* QNetworkAccessManager с системным DNS
* Отдельные реализации DoH и HTTPS

## Итог решения

Выбранный вариант: «Один клиент pinnedHttp», потому что он соединяется с нужным IP, передаёт имя хоста в SNI и закрывает сокет по токену отмены.

### Последствия

* Хорошо: экономия 12 ч в F-03 (раунд 1)
* Хорошо: одна точка для тайм-аутов и отмены
* Плохо: нужен собственный разбор HTTP-ответа

### Подтверждение

Тест с локальным сервером, не завершающим TLS-рукопожатие: отмена менее 1,5 с.

## Плюсы и минусы вариантов

### Один клиент pinnedHttp(ip, url) на QSslSocket (Schannel) для DoH и /cdn-cgi/trace

* Хорошо, потому что проверка идёт на IP от проверяемого DNS
* Хорошо, потому что одна точка отмены
* Плохо, потому что свой разбор HTTP

### QNetworkAccessManager с системным DNS

* Хорошо, потому что готовый HTTP-клиент
* Плохо, потому что использует системный DNS — проверка теряет смысл
* Плохо, потому что отмену зависшего TLS не удаётся гарантировать за 1,5 с

### Отдельные реализации DoH и HTTPS

* Хорошо, потому что каждая реализация проще
* Плохо, потому что двойной объём кода и тестов (+12 ч)
* Плохо, потому что две разные политики тайм-аутов
